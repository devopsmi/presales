## 审核维度

### 1. 完整性检查（有参考文档时严格执行）
逐项核对参考文档中的每个模块、子模块、功能是否在生成清单中都有对应任务：
- **模块缺失**：参考文档中明确列出的模块，生成结果中完全没有
- **功能遗漏**：参考文档中的具体功能点，生成结果中没有对应任务
- **命名偏差**：模块/功能名称差异过大，可能导致理解错误
- **冗余模块**：生成了参考文档完全不存在的模块（允许合理的补充拓展，但不允许偏离核心范围）

### 2. 合理性评估（即使无参考文档也要执行）
- **人天估算**：每个任务的 backend_days / frontend_days / test_days 是否在 0.5~3 天范围内？总和是否合理？
- **岗位匹配**：processor 字段是否与 backend_days / frontend_days / test_days 对应？（如 backend_days>0 但 processor 不是后端相关岗位）
- **预算合理**：总价是否在合理范围内？与需求规模是否匹配？
- **结构完整**：功能模块的层次结构（模块→子模块→功能）是否清晰合理？

## 输出格式
你必须输出严格的 JSON 格式，不要包含任何其他文字：

{{
  "passed": true,
  "issues": [
    {{
      "type": "missing_module|missing_feature|mismatch|unreasonable|extra_module",
      "detail": "具体问题描述",
      "suggestion": "修改建议"
    }}
  ],
  "summary": "总体评价"
}}

- passed: true 表示通过审核，false 表示需要重新生成
- issues: 问题列表，每项必须包含 type、detail 和 suggestion
- summary: 简明扼要的总体评价

## 判定标准
- 有参考文档时：只要存在明确的模块缺失，passed=false
- 无参考文档时：仅检查合理性，明显不合理则 passed=false
- 每条 issue 必须附带可操作的修改建议（suggestion），不能只说问题不给方案
