# AI 软件方案设计 Agent — 实现方案

**基于 README.md V2.0 技术设计文档制定**

## 一、技术栈

| 层级 | 技术选型 | 说明 |
|------|----------|------|
| 后端框架 | FastAPI (Python ≥3.11) | 异步高性能，原生 Pydantic 支持 |
| 包管理 | uv | 项目已有，虚拟环境隔离 |
| LLM 调用 | httpx + OpenAI 兼容接口 | 统一封装，支持多种模型 |
| 文档解析 | pymupdf (PDF), python-docx (Word) | 主流稳定方案 |
| 前端框架 | Vue 3 + TypeScript + Vite | 组合式 API，类型安全 |
| HTTP 客户端 | axios | 支持文件上传与进度 |
| Markdown 渲染 | marked + highlight.js | 轻量代码高亮 |
| 状态管理 | 组件内状态 + composable | 单页面无需 Pinia |

## 二、后端架构

### 2.1 目录结构

```
backend/
├── main.py                    # FastAPI 应用入口，注册路由
├── pyproject.toml             # 依赖管理（uv）
├── .env.example               # 环境变量模板
├── app/
│   ├── __init__.py
│   ├── config.py              # 配置管理（API Key、Model 等）
│   ├── schemas.py             # Pydantic 模型：请求/响应定义
│   ├── router.py              # POST /generate 路由
│   ├── workflow.py            # Pipeline 编排器：顺序调用各 Agent
│   ├── parser/
│   │   ├── __init__.py
│   │   └── document_parser.py # 解析 PDF / Word / txt
│   ├── agents/
│   │   ├── __init__.py
│   │   ├── base.py            # BaseAgent：统一 LLM 调用封装
│   │   ├── requirement_agent.py
│   │   ├── architecture_agent.py
│   │   ├── split_agent.py
│   │   └── estimate_agent.py
│   ├── prompts/
│   │   ├── __init__.py
│   │   ├── requirement.txt
│   │   ├── architecture.txt
│   │   ├── split.txt
│   │   └── estimate.txt
│   └── formatter.py           # 合并各 Agent 结果为最终响应
```

### 2.2 核心数据流

```
POST /generate (需求文本 + 可选文件)
  │
  ▼
DocumentParser.parse()
  └─ 返回统一纯文本
  │
  ▼
WorkflowController.run(context)
  │
  ├─ RequirementAgent
  │   └─ 分析项目目标、用户角色、业务流程 → Markdown
  │
  ├─ ArchitectureAgent
  │   └─ 设计系统架构、模块关系、数据库/API 建议 → Markdown
  │
  ├─ SplitAgent
  │   └─ 将模块拆分为细粒度开发任务 → Markdown
  │
  └─ EstimateAgent
      └─ 根据拆分结果估算工作量与成本 → JSON
  │
  ▼
Formatter.merge()
  └─ 组装最终 GenerateResponse
```

### 2.3 Agent 通信协议

每个 Agent 从 `context` 字典读取上游结果，写入自己的结果：

```python
context = {
    "requirement_text": "...",      # 原始需求 + 文档内容
    "requirement_result": "...",    # RequirementAgent 输出 Markdown
    "architecture_result": "...",   # ArchitectureAgent 输出 Markdown
    "split_result": "...",          # SplitAgent 输出 Markdown
    "estimate_result": {...},       # EstimateAgent 输出 JSON
}
```

### 2.4 Prompt 设计原则

- 每个 Prompt 包含：角色定义 + 上下文输入 + 输出格式约束
- 输出格式约束使用明确标记（如 `你必须输出 JSON，格式如下：`）
- Estimate Prompt 在输出中要求严格 JSON schema，使用 few-shot 示例

### 3.2 组件职责

| 组件 | 职责 | 状态 |
|------|------|------|
| `InputPanel.vue` | 需求文本输入框、文件上传（拖拽/点击）、生成按钮、loading 态 | 输入未提交时显示，生成后折叠或禁用 |
| `MarkdownView.vue` | 接收 markdown 字符串，渲染为 HTML（含代码高亮） | 仅在有结果时渲染 |
| `EstimateTable.vue` | 表格展示 tasks 数组，支持按列排序、关键词搜索、分页 | 仅在有结果时渲染 |
| `SummaryCards.vue` | 4 张卡片：总人天 / 预计周期 / 团队人数 / 研发成本 / 建议报价 | 仅在有结果时渲染 |
| `useGenerate.ts` | 管理 `loading`、`error`、`result` 状态，调用 API | — |

## 五、架构决策记录

### ADR-1：不使用 LangGraph / 多 Agent 编排框架

- **状态**：已接受
- **上下文**：MVP 阶段仅需顺序 Pipeline
- **决策**：使用简单的 WorkflowController 顺序调用
- **后果**：后续如需并行或条件分支，可替换为 LangGraph

### ADR-2：Agent 间通过共享 context 字典通信

- **状态**：已接受
- **上下文**：每个 Agent 需要上游 Agent 的输出
- **决策**：每个 Agent 从 context 读取输入，将结果写回 context
- **后果**：简单直观，易于调试，但需注意 context 字段命名规范

### ADR-3：不使用 UI 框架库

- **状态**：已接受
- **上下文**：单页面应用，交互复杂度低
- **决策**：手写 CSS，仅依赖 marked + highlight.js
- **后果**：bundle 更小（预计 <100KB gzip），灵活度更高

### ADR-4：Python 版本设为 ≥3.11

- **状态**：已接受
- **上下文**：原 .python-version 为 3.13
- **决策**：降为 3.11 以确保 pymupdf / python-docx 兼容性
- **后果**：需更新 .python-version 文件

## 六、MVP 不实现（明确边界）

以下功能已确认不在 MVP 范围内，但设计中已预留扩展点：

| 功能 | 预留方式 |
|------|----------|
| 登录/权限 | 不在路由层处理 |
| 数据库存储 | 所有数据在内存中流转 |
| 多项目/历史记录 | 前端不实现路由，后端不做持久化 |
| RAG | context 字典预留 `retrieved_docs` 字段 |
| 流式输出 | BaseAgent 预留 `stream` 参数 |
| Word/PDF 导出 | 前端不做导出功能 |
| Mermaid/PlantUML | Markdown 不做图表渲染 |
| Docker | 不提供 Dockerfile |
