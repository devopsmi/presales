# 步骤拆解估算方案

## 适用场景
适用于开发流程成熟、功能项可清晰拆解为连续开发步骤的项目。能提供最精确的工时依据。

## 核心原则
每个叶子行（sub_function + description）是最小交付单元。在脑中将其拆解为具体的开发动作，逐步估算每个动作的耗时，汇总后转换为人天。

## 估算方法

### 第一步：心理拆解（不输出）
对每个叶子行和每个参与的工种，在脑中列出该工种要做的具体动作：

**前端开发 (frontend) 典型动作链**：
UI组件开发 → 表单校验/交互逻辑 → 状态管理 → 接口联调 → 交互细节打磨 → 自测

以"多条件筛选搜索"为例：
- 筛选表单组件开发：1.0h
- 表单校验逻辑：0.5h
- 筛选条件状态管理：0.5h
- 与后端接口联调：0.5h
- 列表刷新/loading/空状态：0.5h
- 自测与bug修复：0.5h
- 合计：3.5h

**后端开发 (backend) 典型动作链**：
接口参数设计 → 入参校验 → 业务逻辑 → 数据库操作 → 异常处理 → 单元测试 → 接口文档

以"多条件筛选搜索"为例：
- 查询参数定义与校验：0.5h
- 多条件动态查询逻辑：1.5h
- 权限过滤与数据脱敏：0.5h
- 分页与排序实现：0.5h
- 单元测试：0.5h
- 接口文档：0.3h
- 合计：3.8h

### 第二步：隐性工作补全
每个叶子估算必须覆盖以下隐性工作（估算偏差的主要来源）：

- **自测与修复**：开发工时的基础上增加 20%-30%
- **联调对接**：feature 类叶子每个工种 +0.3~0.5 人天
- **文档与评审**：后端/设计每个叶子 +0.2 人天
- **沟通损耗**：所有工时叠加 10%-15% 的会议/沟通/任务切换时间

### 第三步：理想工时 → 人天转换
- 汇总单叶子所有步骤工时（含隐性工作）
- 除以 8（每天 8 工作小时）
- 四舍五入到 0.5 人天粒度
- 示例：3.5h 理想工时 → 叠加 40% 损耗 = 4.9h → 4.9/8 = 0.61 → 0.5 人天
- 示例：5h 理想工时 → 叠加 40% 损耗 = 7h → 7/8 = 0.88 → 1.0 人天

### 第四步：跨行一致性校准
完成所有叶子估算后，横向检查：
- 同一模块下、复杂度相似的叶子，估算值是否接近？
- 某个叶子的估算是否明显偏离同类？如有偏差，调整并简要写 remark

## 各工种估算参考

**前端开发 (frontend)**
- 单一组件/简单页面：0.5-1 人天
- 表单+列表+中等交互：1-2 人天
- 图表/实时数据/复杂状态机：2-4 人天
- design 行：填 null（系统设计类不涉及前端实现）

**后端开发 (backend)**
- 单表 CRUD 接口：0.5-1 人天
- 多表关联/复杂业务逻辑/文件处理：1-3 人天
- 实时处理/第三方集成/复杂权限：3-5 人天
- design 行：2-5 人天（架构设计、技术选型、方案文档）

**UI设计 (design)**
- 基于组件库的标准页面：0.5 人天
- 需要自定义设计的关键页面：1-2 人天
- 品牌定制/完整设计体系：2-3 人天
- design 行：1-3 人天（设计体系、组件规范）

**测试 (testing)**
- 单个 feature 叶子功能测试：0.3-0.5 人天
- 测试用例编写 + 执行 + 缺陷验证
- design 行通常不涉及测试（填 null）

**项目管理 (pm)**
- 按总工时的 10% 估算，简单项目至少 1 人天
- distribute 到各行或单独汇总

**DevOps (devops)**
- 仅涉及部署/CI/CD/环境搭建的叶子
- 1-3 人天

**数据分析 (data)**
- 仅涉及数据建模/报表/ETL 的叶子
- 1-3 人天

**AI/算法 (ai)**
- 仅涉及 AI 功能的叶子
- 最少 2 人天起步

## 输出格式
只输出纯 JSON 数组，trades 字段已填充。不要输出拆解步骤。

## 约束
- 人天粒度：0.5
- 已选工种全部填写，不参与的填 null
- design 行前端填 null
- 单个叶子单个工种一般不超过 5 人天（超过说明该继续拆）
- 总人天合理，避免过度估算
