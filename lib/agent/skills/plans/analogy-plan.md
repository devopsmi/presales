# 类比参照估算方案

## 适用场景
适用于有成熟历史数据积累的团队，或项目中存在大量相似形态的功能（如多个 CRUD 页面、多个数据看板）。通过比照已完成的同类功能来校准估算。

## 核心原则
LLM 拥有海量的软件项目知识。利用这一优势：对每个叶子行，找到最接近的"典型功能模式"，以该类功能的标准工时为基础，根据当前叶子的具体差异微调。

## 估算方法

### 第一步：识别功能模式（不输出）
对每个叶子行，判断它属于哪种典型的功能模式：

- **列表查询页**：筛选表单 + 数据表格 + 分页 + 详情跳转
  标准基线：前端 1.5 人天，后端 1.0 人天
- **表单录入页**：表单校验 + 提交 + 草稿保存
  标准基线：前端 1.0 人天，后端 0.5 人天
- **数据看板/图表**：图表组件 + 数据聚合 + 实时刷新
  标准基线：前端 2.0 人天，后端 2.0 人天
- **详情展示页**：信息展示 + 状态流转 + 操作按钮
  标准基线：前端 1.0 人天，后端 0.5 人天
- **文件上传处理**：上传组件 + 格式校验 + 解析 + 存储
  标准基线：前端 1.0 人天，后端 1.5 人天
- **消息/通知**：推送 + 列表 + 已读状态
  标准基线：前端 0.5 人天，后端 1.0 人天
- **权限/角色管理**：RBAC + 权限树 + 角色分配
  标准基线：前端 1.5 人天，后端 2.0 人天
- **工作流/审批**：流程配置 + 节点流转 + 审批操作
  标准基线：前端 2.0 人天，后端 3.0 人天
- **数据导入导出**：模板下载 + 批量导入 + 校验 + 导出
  标准基线：前端 1.5 人天，后端 1.5 人天
- **搜索/全文检索**：索引 + 高亮 + 高级筛选
  标准基线：前端 1.0 人天，后端 2.0 人天

### 第二步：复杂度差异微调
确定基线后，根据当前叶子的具体差异调整：

**调高系数（×1.2 ~ ×1.5）**：
- description 提到"实时"、"大屏"、"多端"、"高并发"
- 涉及第三方系统对接
- 数据量级大（百万级+）
- 需要自定义 UI 而非组件库

**调低系数（×0.7 ~ ×0.9）**：
- description 非常简洁，功能单一
- 纯静态页面，无交互
- 基于成熟组件库，无定制
- 仅配置/参数调整，无编码

### 第三步：隐性工作补全
标准基线工时已含基本开发，但需额外计入：
- 联调对接：feature 叶子 +0.3~0.5 人天
- 文档与评审：每个叶子 +0.2 人天
- 沟通与会议损耗：总工时 +15%

### 第四步：同批次交叉校准
估算完所有叶子后，检查：
- 同一模块下相同功能模式的叶子，估算值是否一致？
- 是否有叶子明显偏离模式基线？
- 如有偏差，在 remark 中简要说明原因（如"含第三方地图SDK集成"）

## 各工种特殊性

**前端开发 (frontend)**
- 页面型功能按上述模式基线估算
- design 行：填 null
- 含动画/3D/WebSocket 等复杂交互，在基线基础上 ×1.3~×1.5

**后端开发 (backend)**
- CRUD 型按模式基线；含复杂查询/事务/消息队列 +0.5~1 人天
- design 行：2-5 人天（系统设计、架构方案）

**UI设计 (design)**
- 基于组件库的页面：0.5 人天
- 需自定义视觉的页面：1-2 人天
- design 行：1-3 人天（设计规范、组件体系）

**测试 (testing)**
- 按功能模式复杂度：简单 0.3 / 中等 0.5 / 复杂 1.0 人天/叶子
- 或按总开发人天的 15%-25% 汇总
- design 行通常填 null

**项目管理 (pm)**：总工时的 10%，最少 1 人天

## 输出格式
只输出纯 JSON 数组，trades 字段已填充。不要输出类比过程。

## 约束
- 人天粒度：0.5
- 已选工种全部填写，不参与的填 null
- design 行前端填 null
- 估算值应基于模式基线，不要凭空随意给数
